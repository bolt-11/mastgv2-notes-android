## 1. Explanation

### 1.1 Status of This Test: Official Placeholder

This needs to be emphasized up front: MASTG-TEST-0237 is currently marked **`status: placeholder`** in its official source. This means there is **no** formal Overview, Steps, Observation, or Evaluation section published by MASTG for this test — the only content available is a brief `note` metadata field:

> *"Cross-platform frameworks (e.g. Flutter, React Native, ...), typically have their own implementations for HTTP libraries, where cleartext traffic can be allowed."*

Because the official structure is not yet complete, this document is built primarily from **independent research and the official documentation of each framework** (Flutter, React Native, Cordova), following the research standard applied throughout this document series — rather than from direct quotations of MASTG "Steps/Observation/Evaluation" as in other tests, since those sections have not actually been written by MASTG yet.

### 1.2 Why This Test Must Stand Alone, Separate from MASTG-TEST-0235

MASTG-TEST-0235 tests `android:usesCleartextTraffic` and the Network Security Configuration (NSC) — a mechanism that operates at **Android's native networking layer** (`HttpsURLConnection`, `OkHttp`, the built-in `WebView`, and most HTTP libraries that build their connections through Android's system socket APIs).

The problem: **many cross-platform frameworks do not fully use that native networking layer** — they bring their own runtime and/or HTTP client implementation that runs **on top of** Android rather than being fully integrated with it. This means an NSC configuration that looks perfectly correct in `AndroidManifest.xml`/`network_security_config.xml` **may not apply at all** to traffic generated by that cross-platform layer — a gap that would never be revealed simply by running MASTG-TEST-0235.

### 1.3 The Flutter Case: The Most Significant Finding — NSC Does Not Apply to Dart Traffic

This is the most important research finding for this test, and the most extreme example of the gap described in §1.2.

**Flutter does not use the Java/Kotlin Android networking stack at all** for its built-in HTTP client (`dart:io HttpClient`, and popular libraries built on top of it such as `package:http` and `dio`). Instead, the Flutter engine builds socket connections **directly from the Dart VM**, with TLS implemented using **BoringSSL bundled directly into `libflutter.so`** — completely separate from the Android operating system's trust store and network policy.

As a consequence, according to the Flutter community's own research (GitHub issue `flutter/flutter#106678`, *"Flutter doesn't respect Android's `android:usesCleartextTraffic="false"` settings"*):

- Flutter **previously** had partial support for reading Android's Network Security Configuration via `ApplicationInfoLoader.java` at the engine level.
- This support was **removed** via a pull request titled *"Turn off insecure socket policy configuration in the engine"*, which hardcoded `may_insecurely_connect_to_all_domains = true` and emptied out the entire network domain policy.
- The issue reporting this problem was **closed as "not planned"** by the Flutter team — indicating the Flutter team **has no plans** to restore full NSC enforcement support at the engine level for all cases.

**Critical implication for testers:** a Flutter application can have a `network_security_config.xml` that looks perfect (passing MASTG-TEST-0235 cleanly) — yet the application's Dart code (business logic, not `WebView`) can still send plaintext HTTP without being blocked at all, because **the socket being used belongs to the Dart VM, not a socket subject to Android's policy**. This is why MASTG-TEST-0235 is **not sufficient** for Flutter-based applications, and why this test (0237) must be run as a separate check targeting the framework's own configuration, rather than pure Android configuration.

> **Important note on conflicting sources:** A number of third-party articles (including popular Flutter security guides) still recommend NSC as the primary mitigation for blocking cleartext in Flutter applications, without mentioning the limitation above. Based on primary research directly into the official `flutter/flutter` bug report, **that claim cannot be fully relied upon** for traffic generated directly from Dart code (`dart:io`, `package:http`, `dio`) — NSC is most likely **only effective** for components that actually run on top of Android's native WebView (e.g. `flutter_webview_plugin`/`webview_flutter`, which internally use `android.webkit.WebView`), not for direct HTTP calls from Dart. Testers **must verify this empirically** (§3.4) for the specific version of the Flutter engine used by the target application, rather than assuming based on any documentation — including this one.

### 1.4 The React Native Case: Generally Safer, But Not Always

Unlike Flutter, **React Native's built-in networking modules (`fetch`, `XMLHttpRequest`) on Android are generally implemented on top of OkHttp** — a Java/Kotlin HTTP client library that **does** honor Android's Network Security Configuration. This means that for the most common case, MASTG-TEST-0235 **is sufficiently relevant** to cover React Native's main networking path.

However, there are important exceptions that need to be checked:

- **`react-native-webview`**: The React Native WebView component has a history of similar issues (`react-native-webview#3142` — *"Enable Cleartext traffic inside React Native Webview in Android"*) where cleartext behavior for content loaded by the WebView is not always consistent with the parent application's NSC configuration, depending on the library version and how the WebView is initialized.
- **Custom native modules**: If the application has a custom Java/Kotlin native module that builds its own network connections (outside the standard RN `fetch`/`XMLHttpRequest`) using a library other than OkHttp (e.g. raw `SSLSocket` — see MASTG-TEST-0234), NSC still applies as long as that library actually uses Android sockets — but this must be verified per module, not assumed.
- **Metro bundler / dev server**: During development, RN by default requires cleartext access to the bundler via `localhost` (`facebook/react-native#22375`) — this is legitimate for debug builds but it **must be verified not to carry over** into the release configuration (the same risk pattern discussed in MASTG-TEST-0235 §1.3 regarding `localhost` domain-config).

### 1.5 The Cordova/Ionic Case (WebView-based Hybrid Apps)

Cordova applications (and derivatives such as Ionic with Capacitor) are essentially a **WebView** running HTML/JS/CSS — so their main network traffic (fetch/XHR from JavaScript inside the WebView) **generally follows** the behavior of `android.webkit.WebView`, which in turn **does** honor Android's Network Security Configuration since API 24+.

Even so, the Cordova ecosystem has a well-known history of cleartext issues within its own community:

- The **`net::ERR_CLEARTEXT_NOT_PERMITTED`** error is a common complaint Cordova developers have searched for since Android 9 was released — common enough that dedicated community plugins such as `cordova-plugin-enable-cleartext-traffic` emerged specifically to automatically inject `usesCleartextTraffic="true"` into the built manifest.
- If such a plugin is **left installed in a production build** (rather than only for development needs), it effectively creates a FAIL condition identical to MASTG-TEST-0235, but the source of the problem comes from **cross-platform plugin configuration**, not a developer's manual edit to `AndroidManifest.xml` — making it easy to miss in a code review that only examines the manually written manifest.
- `cordova-plugin-whitelist` controls which domains the WebView is allowed to access/navigate to (`<allow-navigation>`, `<access origin>` in `config.xml`) — this is a separate control from cleartext, but it is often configured together and both need to be checked.

## 2. Tools Used for Testing

### 2.1 Required Tools (Core)

| Tool | Function |
|---|---|
| **jadx / apktool** | Extraction of the manifest, NSC, and resources for basic inspection (same as MASTG-TEST-0235) |
| **grep / ripgrep** | Searching for framework-specific configuration inside `assets/flutter_assets/`, the React Native JS bundle, or Cordova's `config.xml` |
| **Framework detection** (`apkid`, manual APK structure inspection) | Mandatory first step: identify the framework being used (`libflutter.so` indicates Flutter, `libreactnativejni.so`/`index.android.bundle` indicates React Native, `cordova.js`/`config.xml` indicates Cordova) before deciding on the relevant testing method |

### 2.2 Framework-Specific Tools

| Framework | Tool/Technique | Function |
|---|---|---|
| **Flutter** | **Reflutter** / **Fridantic** | Instrumentation of the Flutter engine for hooking at the Dart VM level — needed because standard Frida hooks for Java APIs (`javax.net.ssl.*`) **will never be triggered** by Dart traffic |
| **Flutter** | `strings`/`rabin2` on `libflutter.so` and `libapp.so` | Searching for hardcoded endpoint strings, because standard Java/Kotlin decompilation analysis (jadx) **cannot read Dart code** that has been AOT-compiled into `libapp.so` |
| **Flutter** | **Blutter** / **doldrums** (dedicated Dart snapshot decompilers) | Extracting and analyzing compiled Dart code from `libapp.so` to statically discover HTTP client configuration |
| **React Native** | `react-native-decompiler` / extraction of `index.android.bundle` | The RN JS bundle (usually at `assets/index.android.bundle`) can be extracted and analyzed as JavaScript text to search for `fetch`/`XMLHttpRequest` configuration and hardcoded endpoints |
| **Cordova** | Extraction of `assets/www/` | A Cordova application's HTML/JS/CSS code is stored as raw files in `assets/www/` — directly readable/greppable without any decompilation |
| **Cordova** | Inspection of `res/xml/config.xml` | Searching for `<allow-navigation>`, `<access>`, and the presence of cleartext plugins such as `cordova-plugin-enable-cleartext-traffic` in `plugins/` |

### 2.3 Dynamic Supporting Tools

| Tool | Function |
|---|---|
| **mitmproxy / Burp Suite / PCAPdroid** | Definitive cross-framework evidence — captures raw packets regardless of which layer generated them (Dart, JS bridge, or native Java) |
| **Frida + Reflutter (Flutter-specific)** | Hooking at the Dart runtime level to directly capture `dart:io HttpClient` calls |
| **adb logcat** | Baseline — checking whether the system's `NetworkSecurityConfig` message appears at all while that framework's traffic occurs (if it does not appear, this is strong evidence the traffic does not go through a path subject to NSC) |

### 2.4 Environment Prerequisites

- **Identifying the framework first** is a mandatory first step — the testing methodology is completely different between Flutter, React Native, and Cordova.
- **Static analysis of Dart code requires dedicated tooling** (Blutter/doldrums) that is completely different from the standard Java/Kotlin toolchain (jadx) used in almost every other document in this research series.
- **Dynamic testing with raw network capture (mitmproxy/PCAPdroid) is the most reliable method** for all types of cross-platform frameworks, because it does not depend on assumptions about which layer handles the request — this is consistent with the "trust runtime evidence" principle repeatedly emphasized throughout this MASVS-NETWORK document series.

## 3. Testing Methodology

Because there are no official MASTG steps for this placeholder test, this section is built purely from independent research per framework.

### 3.1 Step 0 — Identify the Cross-Platform Framework Used

```bash
unzip -l target-app.apk | grep -E "libflutter\.so|libapp\.so|libreactnativejni\.so|index\.android\.bundle|cordova\.js|config\.xml"
```

| Evidence found | Indicated framework |
|---|---|
| `lib/*/libflutter.so`, `lib/*/libapp.so`, `assets/flutter_assets/` | **Flutter** |
| `lib/*/libreactnativejni.so`, `assets/index.android.bundle` | **React Native** |
| `assets/www/cordova.js`, `res/xml/config.xml` with Cordova schema | **Cordova/Ionic (Capacitor)** |

### 3.2 Method A — Flutter: Static NSC Configuration Analysis + Empirical Verification of Its Enforcement

```bash
# 1. Still check NSC as in MASTG-TEST-0235 (baseline, though its enforcement must be verified — §3.4)
jadx --no-src -d ./out target-app.apk
grep -i "networkSecurityConfig\|usesCleartextTraffic" ./out/resources/AndroidManifest.xml

# 2. Search for HTTP endpoint strings inside the Dart binary (libapp.so) — Java decompilation CANNOT read this
find . -name "libapp.so" -exec rabin2 -zz {} \; | grep -oE 'http://[a-zA-Z0-9./?=&_-]+'

# 3. Search for references to popular HTTP packages used (for risk context)
grep -r "dart:io\|package:http\|package:dio" ./pubspec.lock 2>/dev/null   # if source is available (whitebox)
```

For deeper analysis of compiled Dart bytecode (blackbox, from the APK alone):

```bash
# Blutter — Dart AOT snapshot decompiler
python3 blutter.py ./out/lib/arm64-v8a/ ./blutter_output/
grep -r "http://" ./blutter_output/
```

### 3.3 Method B — React Native: Extraction and Analysis of the JS Bundle

```bash
unzip -o target-app.apk assets/index.android.bundle -d ./rn_extracted

# The bundle is usually minified; unpack/format it first for workable analysis
npx js-beautify ./rn_extracted/assets/index.android.bundle > ./rn_extracted/bundle_formatted.js

# Search for fetch/XMLHttpRequest patterns with http:// URLs
rg -n 'http://[a-zA-Z0-9./_-]+' ./rn_extracted/bundle_formatted.js
rg -n 'fetch\(["\x27]http://' ./rn_extracted/bundle_formatted.js

# Verify NSC (relevant for RN, unlike Flutter — see §1.4)
grep -i "networkSecurityConfig\|usesCleartextTraffic" ./out/resources/AndroidManifest.xml
```

For more structured results (recovering some variable/function names if a source map is available):

```bash
react-native-decompiler -i ./rn_extracted/assets/index.android.bundle -o ./rn_decompiled/
```

### 3.4 Method C — Empirical Verification "Does NSC Actually Apply?" *(MANDATORY for Flutter, per §1.3)*

This is the most important method in this entire document — per the warning in §1.3, claims from documentation (including this document) **must not be trusted without verification** for the specific version of the Flutter engine used by the target application:

```bash
# 1. Apply the strictest possible NSC: block ALL cleartext
cat > network_security_config_test.xml << 'EOF'
<network-security-config>
    <base-config cleartextTrafficPermitted="false" />
</network-security-config>
EOF
# (rebuild a test APK with this configuration if doing whitebox testing,
#  or use the original APK if it already has a similarly strict NSC)

# 2. Run the application with a proxy that ONLY accepts cleartext HTTP (not HTTPS)
#    on an endpoint known to be called by the application
mitmproxy --mode transparent --set http2=false

# 3. Observe: does an HTTP request from the Dart/JS code still SUCCEED in being sent
#    even though NSC should block it?
```

If the request **still succeeds** even though NSC explicitly forbids cleartext — this is definitive proof that this framework's traffic **does not** obey Android's NSC, confirming the condition described in §1.3 for Flutter.

### 3.5 Method D — Cordova: Inspecting `config.xml` and Cleartext Plugins

```bash
unzip -o target-app.apk res/xml/config.xml -d ./cordova_check
cat ./cordova_check/res/xml/config.xml | grep -i "allow-navigation\|access origin\|cleartext"

# Search for traces of third-party cleartext plugins that may have been left over from development
unzip -l target-app.apk | grep -i "cleartext"
jadx --no-src -d ./out2 target-app.apk
grep -i "usesCleartextTraffic" ./out2/resources/AndroidManifest.xml

# Inspect the WebView application code (assets/www) for HTTP endpoints
unzip -o target-app.apk -d ./cordova_full 'assets/www/*'
rg -n 'http://[a-zA-Z0-9./_-]+' ./cordova_full/assets/www/
```

### 3.6 Method E — Universal Network Capture (Cross-Framework, Most Reliable)

```bash
# PCAPdroid (no root needed, works for all frameworks)
adb shell am start -n com.emanuelef.remote_capture/.activities.CaptureCtrl \
  --es action start --es pcap_dump_mode tcp --es collector_ip 127.0.0.1

# Or mitmproxy with a system CA certificate (root) for full MITM
mitmweb --mode transparent
```

Raw capture **does not care** whether the traffic originates from Dart, a JS bridge, or native Java code — this is why this method serves as the **definitive comparison point** regardless of which framework the target application uses.

### 3.7 Method Comparison: When to Use Which

| Method | Target framework | Answers the question | When to use |
|---|---|---|---|
| **A** | Flutter | Static configuration + verification of NSC enforcement | Mandatory for all Flutter applications |
| **B** | React Native | Hardcoded endpoints in the JS bundle | Mandatory for all RN applications |
| **C** | Flutter (primarily) | **Does NSC actually apply?** | **Mandatory** — do not conclude PASS from static NSC analysis alone on Flutter |
| **D** | Cordova/Ionic | WebView configuration + leftover plugins | Mandatory for all Cordova/Capacitor applications |
| **E** | All frameworks | Definitive field evidence | **Mandatory** as the final confirmation, regardless of framework |

**Minimum combination I recommend:** **0 (framework identification) → framework-specific static method (A/B/D) → E (network capture) as the final proof**. For Flutter specifically, **C must not be skipped** — it is the only way to ensure a configuration that looks safe actually provides real protection.

### 3.8 Evaluation Criteria: Positive Case & Negative Case

Because there is no official Evaluation clause from MASTG (placeholder status), the following criteria are built from the underlying principle of MASWE-0026 (Network Traffic Not Encrypted) that this test is based on, adapted for the cross-platform context.

---

#### ❌ FAIL / ISSUE — The check is declared FAILED if:

| No | Condition |
|---|---|
| F1 | A Flutter application has an `http://` reference confirmed to be called from Dart code (`dart:io`, `package:http`, `dio`), **regardless of** NSC status — because §1.3 shows NSC may be entirely irrelevant for this traffic |
| F2 | Empirical verification (Method C) shows an HTTP request from framework code **still succeeds in being sent** even though NSC explicitly forbids cleartext |
| F3 | The React Native JS bundle contains an `http://` endpoint confirmed to be actively called via `fetch`/`XMLHttpRequest`, **and** NSC does not block it (§1.4 — the RN case where NSC is indeed relevant) |
| F4 | A Cordova/Ionic application has a third-party cleartext plugin (e.g. `cordova-plugin-enable-cleartext-traffic`) that is **still active in the production build**, producing an unintended `usesCleartextTraffic="true"` for release |
| F5 | Real network capture (Method E) shows plaintext HTTP packets actually being sent, regardless of the source code layer |

---

#### ✅ PASS — The check is declared PASSED if:

| No | Condition |
|---|---|
| P1 | No actively used `http://` endpoint is found in the Dart/JS code of any framework |
| P2 | For Flutter: empirical verification (Method C) confirms that **all** endpoints called are indeed `https://`, making the inapplicability of NSC to the Dart socket irrelevant (because there is no cleartext attempt to be blocked) |
| P3 | For React Native: NSC is confirmed (Method C-style verification) to actually block cleartext attempts from `fetch`/`XMLHttpRequest` |
| P4 | For Cordova: `config.xml` and the manifest are clean of cleartext exceptions, and there is no trace of a leftover development cleartext plugin |
| P5 | Thorough network capture (Method E) throughout the full testing session shows only TLS connections |

---

#### ⚠️ Important Notes on Assessment

1. **This is the test that demands empirical verification most heavily among the entire MASVS-NETWORK test series discussed so far.** Because of its placeholder status and the fast-changing cross-platform framework landscape (Flutter's behavior regarding NSC has even changed between engine versions, per the history in GitHub issue #106678), **never conclude a result from reading framework documentation alone** — always verify with Method C/E on the framework version actually used by the target application.

2. **For Flutter, a PASS on MASTG-TEST-0235 provides no guarantee whatsoever for this test.** To repeat: an application can pass MASTG-TEST-0235 perfectly and still FAIL entirely here, because Dart traffic does not obey the mechanism checked by MASTG-TEST-0235.

3. **Static analysis of compiled Dart code is far more difficult than Java/Kotlin.** Tooling such as Blutter is still considered active research and is not as reliable as jadx is for Java code — if static analysis is not possible/incomplete, **increase the weight placed on dynamic testing (Method C/E)** as the primary source of truth.

4. **Pay specific attention to the framework version when reporting findings.** Because this behavior is an engine/design decision that can change between releases (as in Flutter's history in §1.3), test reports **must state the version of Flutter/React Native/Cordova** tested so findings can be reproduced and are not misleading when read after that framework releases a new version.

5. **Severity is modulated by the framework and the type of data involved:**

   | Factor | Severity |
   |---|---|
   | Flutter sends sensitive data over `http://` — NSC is entirely irrelevant | **Critical** — the common misconception that NSC already closes this gap often means the risk goes unnoticed by the development team |
   | React Native sends sensitive data over `http://` without NSC blocking it | **Critical** |
   | A Cordova development cleartext plugin left in the production release | **High** |
   | The HTTP endpoint is only used for non-sensitive communication (health check, version check) | **Medium/Low** |

6. **Document:** the exact framework and version, the identification results (§3.1), the NSC status in the manifest, the results of empirical verification (§3.4) proving/disproving NSC enforcement for that framework, and network capture evidence.

## 4. Recommendations

### 4.1 Flutter: Do Not Rely on NSC — Enforce It at the Dart Code Level

Because NSC may not apply (§1.3), explicitly control the URL scheme at the Dart code level, rather than relying solely on platform configuration:

```dart
// Explicit validation at the application level — do not rely on Android/NSC to block HTTP
Uri buildSecureUri(String url) {
  final uri = Uri.parse(url);
  if (uri.scheme != 'https') {
    throw ArgumentError('Only HTTPS is allowed, found: ${uri.scheme}');
  }
  return uri;
}
```

For `dio`, use an interceptor to enforce this policy centrally:

```dart
dio.interceptors.add(InterceptorsWrapper(
  onRequest: (options, handler) {
    if (!options.uri.toString().startsWith('https://')) {
      return handler.reject(DioException(
        requestOptions: options,
        error: 'Cleartext HTTP is not allowed',
      ));
    }
    return handler.next(options);
  },
));
```

### 4.2 React Native: Keep NSC, Add JS Bundle Auditing to CI/CD

```bash
#!/bin/bash
# ci-check-rn-cleartext.sh
unzip -o "$1" assets/index.android.bundle -d /tmp/rn_check
if grep -q 'http://' /tmp/rn_check/assets/index.android.bundle; then
    echo "[WARNING] Found http:// reference in the React Native JS bundle"
fi
```

### 4.3 Cordova: Remove the Development Cleartext Plugin Before Release

```bash
cordova plugin remove cordova-plugin-enable-cleartext-traffic --save
```

Separate configuration via build variants/environments following the same recommendation as MASTG-TEST-0235 §4.3 — do not let debug plugins/configuration carry over into the production release pipeline.

### 4.4 Re-Verify on Every Framework Version Upgrade

Because this behavior has been proven to change between engine versions (§1.3), make empirical verification (§3.4) a **routine part of the upgrade process** for Flutter/React Native/Cordova — not something done only once at the start of the project.

### 4.5 Remediation Checklist

- [ ] The cross-platform framework in use has been identified, including its version
- [ ] For Flutter: HTTPS scheme validation is explicitly enforced at the Dart code level (interceptor/wrapper), not relying on NSC alone
- [ ] For React Native: NSC is applied and verified to actually block cleartext attempts from `fetch`/`XMLHttpRequest`
- [ ] For Cordova: the development cleartext plugin has been removed from the production build
- [ ] Empirical verification (§3.4) has been performed on the specific framework version in use, rather than assumed from documentation
- [ ] JS bundle/Dart binary auditing is integrated into CI/CD to detect new HTTP endpoints
- [ ] The framework version upgrade process includes re-verification of cleartext behavior
- [ ] **Re-verification:** rerun MASTG-TEST-0237 on the final release APK after remediation and after every framework upgrade

*This document is built primarily from independent research (official Flutter/React Native/Cordova documentation, community bug reports, and third-party security articles) because MASTG-TEST-0237 currently has **placeholder** status and does not yet have an official Overview/Steps/Evaluation. The most significant finding in this research is that Flutter deliberately removed Network Security Configuration enforcement support at the engine level (`flutter/flutter#106678`, closed as "not planned") — a critical gap that makes MASTG-TEST-0235 insufficient to guarantee the network security of Flutter-based applications. Because of its placeholder nature and the ever-changing framework landscape, this document will require periodic updates as Flutter/React Native/Cordova versions evolve and as MASTG publishes official content in the future.*
